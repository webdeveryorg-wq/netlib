## Цель и подтверждённые основания

Снизить число ошибок подключения и выбора лидера, сохранив работу старых вкладок во время поэтапного выпуска. Анализ истории: [отчёт](../../../reports/69212489-netlib-upstream-review.md).

| Рассмотренная вершина upstream | `44c9d0746799c51bf9c652c57162e8b273ed3901` |
| Исходный клиент шахмат | npm `@poki/netlib@0.0.16`, gitHead `9a1a99018f1b2edeb22cc3080f6e76be13591166` |
| Целевой клиент шахмат | npm `@poki/netlib@0.0.20`, gitHead `ade212289848daae29508841b0585a58a547f299` |

Пользователь подтвердил источник клиента. В доступном `D:/Projects/learn-chess/packages/peer/package.json` задан `^0.0.16`, lock-файл и установленный пакет разрешаются в `0.0.16`. Для выпуска проверяется именно опубликованный npm-артефакт `0.0.20`, а не текущий upstream main.

Наш единственный клиентский коммит `1c32a88` меняет ICE для localhost, offer/answer, таймер переговоров и номера каналов. Эти изменения в текущие шахматы не входят. Номера стандартных каналов оригинала: reliable=0, unreliable=1, control=2; у форка: reliable=1, unreliable=2, control=0. Переход на клиентский форк не входит в утверждённую версию 3.

`PeerNetwork` в шахматах явно передаёт STUN и URL сигналинга. URL по умолчанию Poki, но его может переопределять `netlib_host`; фактический флаг production ещё не проверен. Собственный `leave()` обращается к внутренним полям библиотеки и требует проверки с новой версией.

## Объём и решения

| Решение | Статус и последствия |
| --- | --- |
| PD-01: исходный клиент | Закрыто: оригинальный npm `0.0.16` |
| PD-03: целевой клиент | Утверждено: оригинальный npm `0.0.20`, без выпуска `@smartberry/netlib` для шахмат |
| Серверные патчи | #340, #344, #388 и только серверная часть #364 |
| Разделение выпуска | Сначала ручное обновление сервера пользователем; клиент при следующем выпуске шахмат |
| PD-02: окно выкладки | Репетиция: ожидание соперника восстанавливается; подключение и активная партия нарушаются и на новом, и на исходном серверном коде. Рекомендовано окно обслуживания без активных партий/подключений; конкретное окно ещё не выбрано |

Сохраняются wire-форматы действующего сигналинга, схема БД, Cloudflare/STUN fallback, инициализация vector, правила игры, рейтинга, таймеров и существующая политика восстановления. UI, тексты и ассеты не меняются. Обновление оригинального клиента не требует автоматически включать TURN или менять endpoint.

Новая latency-модель и её миграции, toolchain/Dependabot, инфраструктура Poki и перенос собственных клиентских правок форка в шахматы исключены. Библиотека `0.0.20` уже содержит клиентское исправление #364 и исправление legacy-сборки #355. Проверяется весь выпущенный пакет; отдельно выбирать коммиты внутри npm-релиза нельзя.

## Владение и порядок реализации

1. Зафиксировать production SHA/образ, Compose project, тома, override и схему по командам чтения, выполняемым пользователем. Не собирать значения секретов. Сохранить исходную сборку шахмат и образ сервера для отката.
2. Подготовить отдельные PostgreSQL 15/pgvector и Go/CGO-окружение. Выполнить исходные проверки и отделить существующие ошибки от новых.
3. Перенести #340, #344, #388 с указанием происхождения. В серверной части #364 вернуть из `Store.JoinLobby` снимок участников до присоединения внутри транзакции и использовать его в `HandleJoinPacket`.
4. Добавить фокусированные проверки конкурентных входов, лидера и контекстов. Исправить обычный restart; подготовить отдельную процедуру применения нового образа.
5. Выполнить SC-04–SC-08 с опубликованными оригинальными клиентами. Клиентский `lib/` нашего форка не является доказательством проверки шахмат и не меняется в этом этапе.
6. Проверить матрицу совместимости, репетицию обновления и откат. Выдать пользователю конкретные команды для его проверенного развёртывания.
7. Пользователь обновляет сервер. При следующем релизе шахмат обновить зависимость и lock-файл штатным пакетным менеджером, проверить сборку и смешанные вкладки. Игровой адаптер меняется только при доказанной необходимости и согласованном изменении объёма.

## Выпуск и откат

Сначала собрать новый образ при работающем старом. Пересоздать только netlib в прежнем Compose project с прежними томами. Полный `down` и `down -v` не входят в процедуру. Сохранить неизменяемый идентификатор предыдущего образа и проверенную резервную копию БД/сертификатов.

После пересоздания проверить `/health`, `/ready`, настоящий WebSocket через Nginx, создание/поиск/вход и передачу сообщений. Production-preflight уточнил: действующий хостовый Nginx использует `localhost:8080`; сохранение опубликованного порта не требует reload. Для отдельного тестового Nginx с Docker-именем `netlib:8080` при смене адреса контейнера проверять upstream и при необходимости выполнять `nginx -t` и reload.

При регрессии входа, сообщений, лидера, credentials/SDP/ICE или сохранности данных остановить выпуск. Пользователь возвращает прежний образ с теми же томами и повторяет сетевую проверку. Миграции БД не меняются; восстановление схемы для выбранных патчей не требуется. Клиент откатывается возвратом предыдущей версии пакета и сборки шахмат.
